0 한 줄 정의 & 멘탈모델 교정

한 줄: 서울대 거버넌스 자료를 LLM으로 질의응답하는 Next.js 풀스택 웹앱. 다중 위키 자동 라우팅 + 하이브리드 검색(키워드+벡터) + 권한 관리.

네가 알던 것정확히는
"프론트 + 백엔드 + 에이전트 종합"맞음 Next.js = 풀스택(프론트 React + 백엔드 API가 한 프로젝트). "에이전트"는 백엔드 안의 라우팅·검색 로직, 별도 서버 아님.
"Obsidian raw에 넣은 걸 ingest해서 쓴다"맞음 ✓ 거버넌스(사람 수기) + 단과대 Tier1/2(크롤 자동) 둘 다 Obsidian에 .md로 들어가고, 빌드가 거기서 읽어 JSON·임베딩 생성.
"Obsidian data 가져와 로직 씌워 배포"맞음 단 빌드타임(Obsidian→JSON→벡터DB 가공)과 런타임(앱이 가공물을 검색·생성)이 분리. "배포되는 건 앱".
발표 한 문장: "지식을 생산(사람 큐레이션 + 웹 크롤, 둘 다 Obsidian에 축적)하고, 빌드 파이프라인이 검색 가능한 형태(JSON+벡터+DB)로 가공하며, Next.js 앱이 서빙(라우팅→검색→LLM)하는 3계층 구조입니다."

🧭 확대 — fact / insight 판단 에이전트 (§4의 2번 단계)

무엇: 질문을 받으면 Claude Haiku(작고 빠른 LLM)가 "답변 방식"을 분류한다. 도구 없는 단일 호출 = 에이전트라기보다 분류기. 비용 ~$0.001/질문.

모드뜻예
fact자료에 있는 사실을 찾아 보고·나열·비교 (자료가 곧 답)"2026 예산은?" · "이사회 안건 종류" · "역대 총장은?"
insight사실을 넘어 해석·진단·제안·전망·평가"예산 늘릴 방안?" · "왜 채용이 어렵나?" · "이게 최선인가?"

어떻게: 키워드 매칭이 아니라 LLM이 의도를 이해. "무엇/얼마/패턴 보고 → fact" vs "왜/이유/의미/제안 → insight". ⭐ "애매하면 insight" (분석을 fact로 보내면 빈약=나쁜 실수, 반대는 풍부할 뿐=무해 → 안전 방향).

이 판정이 바꾸는 것: ① 웹 fact=내부전용 / insight=web_search   ② 권한 insight=admin·tier1만   ③ 스타일 fact=사실보고 / insight=사실[N]+(해석)(제안)

최근 진화(이번 작업·발표 포인트): 같은 Haiku 1콜이 이제 복잡도·최신성·단과대 신호까지 한꺼번에 출력("QueryPlan")하도록 확장 → 5개 파일에 흩어진 정규식 규칙을 LLM 하나로 통합(새 질문유형마다 규칙 덧대던 유지보수 부채 제거). 실질의 121건 검증 후 배포.

5 핵심 기술 4가지 (발표 포인트)

① 하이브리드 RAG 검색의 핵심

키워드(정확 용어) + 벡터(의미 유사) 병행 → RRF 순위 융합 → rerank 정밀 재정렬 → 예산컷. 벡터=Voyage voyage-4-large(1024d)+pgvector, rerank=Voyage rerank-2.5.

top-K? 각 검색은 top-K(≈30) 후보를 뽑지만, 최종 컷은 고정 top-K가 아니라 rerank + 컨텍스트 예산(글자수) — 단일 top-K로 자르면 특정 위키가 통째로 누락돼 다양성이 붕괴하기 때문(실측 후 그 방식 폐기).

왜? 키워드만으론 동의어("장학금"↔"학생경비")를 놓치고, 벡터만으론 고유명사·정확 수치를 놓침 → 합쳐서 recall+precision 동시 확보.

② 다중 에이전트 자동 라우팅

위키 9(+단과대 28)을 다 검색하지 않고 관련 위키만 자동 선택. 점수+개념색인+의미힌트+갭탐지로 cutoff. wiki_id 격리로 "공대 X"는 공대만 → 교차오염 0.

③ Tier 시스템 단과대 비용·신선도 최적화

Tier콘텐츠저장소서빙

④ 권한 4단계 + 페르소나 Lens

admin/tier1/tier2/pending — 민감자료·업로드·관리자·insight(web) 차등. Lens: 특정 인물 입장(stance)으로 그 사람 시각 분석(admin 전용).

⑤ 웹검색 — fact는 내부 전용, insight만 외부 신뢰 설계

모드웹검색이유
fact (사실 보고)없음 내부 KB만거버넌스 도구가 웹發 사실을 권위 있게 단정하면 신뢰 붕괴 → 외부 필요해도 "범위 밖"으로 정직하게
insight (분석·제안)web_search + 가드내부로 안 풀리면 직접 검색. 나무위키·블로그 하드 차단, 1차 출처만. 내부[N]+🌐외부 이중 인용

권한 격리: insight 자체가 admin/tier1 전용 → tier2·pending은 fact만 → 웹에 절대 도달 안 함.   비용: fact·lens=$0, insight 웹발동=~$0.18~0.36/질의(웹 본문이 입력토큰).

8 현재 상태 & 한계 (정직 — Q&A 대비)

  • 데이터 갱신 일부 수동(wiki:build→embed:build). 게시판은 cron 자동(일 2회).
  • 동적 렌더 게시판 2곳(gsct·gspa) 파싱 실패 → 해당 게시판만 일반자료로 degrade(안전).
  • 모바일 UI 미최적화 · LLM 응답 캐싱 없음.
  • 의도 통합 라우터 방금 라이브 전환 → 모니터링 단계(문제 시 즉시 롤백).
  • 거버넌스 동결 원칙: 기능 추가해도 거버넌스 9위키 동작 byte-identical 유지(회귀 19/19 게이트).

Q. 그냥 ChatGPT에 자료 넣으면 되지 않나?
① 자료가 방대 → 관련 부분만 검색해 넣는 RAG 필요. ② 거버넌스는 출처·정확성이 생명 → 모든 사실에 [N] 인용 + 할루시네이션 가드(P0~P9). ③ 권한별 자료 분리.
Q. 할루시네이션은 어떻게 막나?
검색된 자료에만 근거 + 인라인 [N] 인용 강제 + 결론 단정 금지(P8) + 출처 메커니즘 단정 금지(P9). 못 찾으면 "자료 범위 밖"으로 정직하게.
Q. 위키가 늘면 느려지거나 부정확해지지 않나?
전부 검색 안 하고 라우팅으로 관련 위키만 선택 + 컨텍스트 예산 캡 → 위키 수와 무관하게 비용·속도 일정. wiki_id 격리로 교차오염 방지.
Q. 데이터는 얼마나 최신인가?
거버넌스 수기 갱신, 단과대 게시판은 하루 2회 자동 크롤(live_cache). 정형사실 TTL 90일. 답변에 "수집: 날짜 기준" 표시.
Q. 비용은?
생성=Sonnet(~$0.05~0.15/질의), 라우팅=Haiku(~$0.001). 임베딩·rerank는 Voyage 무료 티어. 게시판 크롤·cron $0(공개 repo).
Q. 검색이 왜 키워드+벡터 둘 다인가?
키워드=정확 용어·고유명사·수치에 강함, 벡터=동의어·의미 유사에 강함. RRF 융합 + rerank로 약점 상호 보완.
