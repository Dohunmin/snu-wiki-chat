# 메시지 프레이밍 에이전트 — 종합 설계 제안

> 독자: 프로젝트 오너(기술). 목적: 이석재 후보의 **실제 입장**을 각 단과대·대학원·투표계층·학생단체가 **자기 언어로** 받아들이도록 재표현하는 캠페인 카피 생성기를, 기존 lens/citation/streaming 기계 위에 최소 배선으로 구축.

## 1. 핵심 개념

### 1.1 한 줄 정의

**프레이밍 에이전트 = 이석재의 검증된 입장([N])을, 청중별 톤으로 "번역"해 지지 설득 카피를 만드는 합성 레이어.** 새 정책 생성기·여론 예측기·자동 발송기가 아니다. 출력은 항상 **admin 전용 초안(draft)**이며 인간 승인 후 사용.

핵심 규율 하나로 압축된다:

> **프레이밍은 번역이지 날조가 아니다 (Framing is translation, not fabrication).**

### 1.2 합성 레이어 통찰 — 4개 축의 런타임 교차

이석재는 철학과 교수·전 인문대학장이고, 그의 9개 stance는 전부 인간 존엄·공동체·개별성·"정답 없는 문제"라는 인문 프레임을 통과한다(`data/leesj.json`). 이건 **자산이자 부채**다 — 인문대엔 홈그라운드, 공대·의대엔 "너무 철학적"이라는 오너가 지목한 정확한 위험. 프레이밍 에이전트가 하는 일은 철학을 *제거*하는 게 아니라 청중의 응용 어휘로 *옮기는* 것이다. **아이디어의 출처는 철학이되, 청중에게 도달하는 표면은 청중의 언어**여야 한다.

이 제품은 4개의 서로 다른 데이터 축을 **생성 시점에** 교차 합성한다 (정적 매핑을 미리 굽지 않음 — 계획서의 런타임 합성 모델과 정합):

```
① 단과대 깊이 (substrate, 읽기전용)   ← data/{college}.json overviews(인사말·비전)=청중 자기 어휘
                                          + entities(학과 훅) + stat-yearbook facts(규모)
② 이석재 stance (grounding, 재사용)    ← data/leesj.json canonical(공약 3대축 L0) + 9 stance(L1)
③ 청중 프로필 (신규 저작, instruction) ← data/audiences.json tone_profile/priorities/pain/landmines
④ 톤 캘리브레이션 (프롬프트 로직)       ← ③의 구조 필드로 ②의 철학 레지스터를 ①의 어휘로 번역
```

①②는 이미 코드베이스에 존재(재사용), ③이 **진짜 신규 자산**, ④가 이 에이전트의 지적 심장이다.

### 1.3 왜 lens와 동형이되 방향이 반대인가

프레이밍은 lens 브랜치(`route.ts:247-277`)를 원형으로 꽂히고 `lens.ts`의 페르소나 주입 기계를 100% 재사용한다. 그러나 프롬프트는 **반전**된다:

- **lens** = 분석가 목소리 + 비판적 거리 + 양면 제시(`prompts.ts:305` "그의 프레임이 유일한 정답인 양 쓰지 말 것"). 매니페스토화 억제.
- **framing** = 전략가 목소리 + 지지 설득 + 청중 톤. 단, **날조·오귀속은 lens보다 더 강하게 차단**(캠페인 카피는 없는 입장을 투사할 유인이 가장 큼).

따라서 `buildFramingSystemPrompt`는 `buildLensSystemPrompt`를 호출하면 안 된다(비판적 거리 지침이 광고와 충돌). 대신 **`buildSystemPrompt`(base P0–P9) + canonicalFrame 개념 재사용 + 신규 advocacy/translation 레이어**로 재조립한다.

`data/leesj.json` 실측: canonical 1건(미래대학 3대축) + stance 9개 + evidence 13개. 커버리지가 **극단적으로 편중**:

  const audience = loadAudienceProfile(audienceId);              // 신규(framing.ts), 동기 JSON

    ...(canonicalCtx ? [canonicalCtx] : []),

  citationMapping = fNumbered.mapping;
  citationSummary = fNumbered.summary;

  systemPrompt = buildFramingSystemPrompt(substrate, persona, audience, role); // 신규(prompts.ts)
  userMessage = buildFramingUserMessage(message, fNumbered.contextMarkdown, fNumbered.summary, audience);

  lensPersonaInfo = {
    id: audience.id,
    displayName: `${persona.displayName} → ${audience.label}`,
    insufficient: persona.stances.length === 0,   // ★ canonical 무시한 stance-only 갭 신호
  };

### 3.2 회수 합성 (`lib/agents/framing.ts` 신규)

세 소스를 생성 시점에 융합:
```
L0  canonical  — leesj 공약 3대축   (loadPersonaContext → canonicalToContext)   [상단 pin]
    substrate  — 단과대 인사말/비전  (loadAudienceSubstrate, 항상 pin)           ← 청중 자기 어휘(톤 앵커)
               + 질의 관련 entity/fact (wikiAgent.getContext, 키워드+RRF)
L1  stance     — leesj RRF top-8    (loadPersonaContext → personaToContext)      [후보 목소리]
```

**신규 회수 primitive 2개** (lens.ts 직접로드 패턴 미러):
- `loadAudienceSubstrate(collegeWikiId, query, role)`: ① `registry.get(collegeWikiId)`로 단과대 WikiAgent 획득 → ② **인사말·비전/인재상 overview를 질의 무관 항상 pin**(톤 앵커 — "연구비" 질문이 인사말을 회수하지 못하므로 강제). 메뉴 크롬 사전 제거. → ③ 질의 관련 entity/fact는 `wikiAgent.getContext`로 키워드+RRF 회수. → `AgentContext[]` 반환 → `buildNumberedContexts`로 직행.
- `loadAudienceProfile(audienceId)`: `data/audiences.json` 동기 읽기 → `AudienceProfile`. **이건 instruction 데이터라 시스템 프롬프트에 주입, `[N]` 컨텍스트엔 넣지 않음**(인용할 사실이 아님).

**무수정 재사용**: `loadPersonaContext`/`canonicalToContext`/`personaToContext`/`buildNumberedContexts`/`CitationRegistry`/`enforceContextBudget`/SSE 루프/`resolveText`·`safeFlushPoint`/부분저장/Sheets/`messages.mode` 저장.

### 3.5 톤 캘리브레이션 메커니즘 ("공대에 과도한 철학 금지" 기능)

오너 난제의 핵심. **두 개의 직교 다이얼**로 분해하는 것이 제품의 지적 자산:

| 다이얼 | 통제 대상 | 낮음 | 높음 |
|---|---|---|---|
| **D1 철학 깊이** | 근본 원리·가치까지 얼마나 파고드나 | 결론·효익만 | 존재론 층위까지 |
| **D2 레지스터** | 어떤 어휘·톤으로 | 공학/데이터/행정 | 성찰/지성/인문 |

- 공대 = **D1 낮음 + D2 공학 레지스터**  · 인문대 = **D1 높음 + D2 인문**  · 직원 = **D1 낮음 + D2 행정/안정**
- **핵심: D1을 0으로 내려도 아이디어의 출처는 철학이다.** 철학을 *제거*가 아니라 *표면에서 안 보이게*. 이게 "철학 베이스 유지 + 청중 맞춤" 동시 만족.

**2계층 인코딩**:
- **계층 1 (청중 전역 하드 게이트)** = `AudienceProfile`의 `abstractionTolerance` + `evidenceMode` + `avoidFrames` + `bannedTerms` + `lexicon`. 프롬프트가 이 청중 답변 전체에 거는 레지스터 게이트. 예: eng는 "추상 철학 연속 3문장 금지, 매 철학 주장은 청중의 구체 이익으로 착지."
- **계층 2 (stance별 번역)** = `resonantStances[].translationNote`. 같은 stance라도 청중마다 다르게 재등록. AI시대역할 stance(원본=존엄성 철학) → eng: "존엄성 프레임 최소화, 'AI×전공 실전 배치'로 진입" / humanities: "존엄성·과학과철학의다리 정면 활용, 성찰 레지스터 OK".

**`translations` few-shot 쌍이 최고 레버**: "공대엔 과도한 철학 금지"를 산문 추론이 아니라 from→to 매핑으로 *조작화*한다. 예: `연구비 절대성` → 공대: "협상 대상이 아니라 경쟁력의 하한선" / 인문대: "지적 자유의 물적 토대".

**철학:실용 비율(P) 산정** (선택적 정교화, admin 슬라이더 override 가능):
```
P = audience.philosophyWeight(기저)      # 인문대70 학생단체50 대학원생45 학부생35 직원25 공대20 의대15
P += 채널: 연설+10 | 이메일0 | 문자/카드뉴스-15
P += 목표: 공감형성+10 | 정책설명·우려불식-10
P += 주제: 철학풍부 stance매칭+10 | 응용 stance매칭-10
→ P가 오프닝 훅 레지스터·(효익:가치 주장 비율)·클로징 앵커 유무를 결정
D2(레지스터)는 P와 무관하게 항상 청중 lexicon 고정
```

### 3.6 가드레일 (가장 중요한 부분)

1. **입장 귀속은 실제 grounding에만 게이트**: "이석재는 X하겠다"는 `[stance][N]`/canonical `[N]` 뒷받침될 때만 허용. 매칭 없으면 그 주제 후보 입장 **단정 금지**.
2. **약/부재 stance → 톤만 빌리고 정책 금지**: `persona.stances.length === 0`(→ `lensPersonaInfo.insufficient`로 UI 노출)이면 canonical 3대축의 *일반 가치*(공동체·개별성·재정지원 절대성·결단)로 톤만 잡고 **구체 정책 약속 생성 금지**. 전략가 추론(③, 조건 어조 "~에 비추어 ~할 여지")으로만.
3. **자체 커버리지-갭 감지기 (필수 — insufficient 무력화 보완)**: leesj는 canonical 상시 pin으로 lens의 `insufficient`가 절대 안 뜬다(`lens.ts:173`). → 프레이밍은 **stance-only 신호**(`persona.stances.length === 0`) + `audience.silenceTopics`로 갭을 자체 감지. off-domain(의대 임상·법·경영·학부생 복지)에서 도메인 특화 입장 생성 차단.
4. **랜드마인 레지스트리**: `audience.landmines[]`를 프롬프트에 "절대 긍정 소재로 쓰지 말 것" 하드룰로 주입. 예: Thiel Fellowship(공대 창업), 의대 정원(하드 차단), '사후 엄벌·결단하는 본부'(직원 → '책임의 상향 배분'으로 재구성).
5. **3 네임스페이스 엄격 분리** (lens 오귀속 가드 재사용): 전략가 제안(③)을 그의 발언처럼 쓰면 차단.
6. **`[N]` floor 유지**: 청중/대학 사실·후보 입장은 인용 유지 → admin이 "어느 주장이 grounded vs 전략적 확장"인지 감사 가능.
7. **갭이면 생성 거부**: 예) 의대 정원 질의 → 본문보다 먼저 최상단 경고 "이석재는 이 주제 공개 입장 없음. 정원 자체 카피는 후보 확인 후에만." (진정성·법적 리스크 방어의 실물)

**출력 포맷** (분석 모드와 구별):
- 📣 헤드라인 (청중 어휘 한 줄)
- 핵심 메시지 3–5개 (청중 톤 설득 문장 + `[N]`/`[stance][N]`)
- ⚠️ 프레이밍 노트 (내부용) — 근거 원장: 어느 것이 실제 입장([stance][N])이고 어느 것이 전략적 확장(③)인지 + 회피한 landmine + 적용 P값 + 커버리지 경고. **admin 투명성 레이어.**

## 4. 단계별 로드맵

**Phase 0 — 데이터 시드 (0.5~1주, 코드 전)**: `audiences.json`에 eng + humanities 2개만 저작(오너가 지목한 톤 양극단). tone_profile + translations + silenceTopics + landmines + 보편앵커5. LLM 합성 초안 → admin 1회 검수(`llm-synth-reviewed`). college 인사말/비전에서 lexicon 추출.

**Phase 1 — thin vertical slice (1~1.5주)**: `framing.ts` 로더 + `buildFramingSystemPrompt`(방향 반전) + route.ts 브랜치 + 자체 갭 감지기 + 랜드마인. admin 전용, 웹 OFF. **lens의 stance retrieval·CitationRegistry·SSE·messages.mode 저장 전부 재사용.** 가장 어려운 케이스(공대 vs 인문대)에서 register-transfer 검증 후 확장. 워크드 예시(공대/연구비/이메일 P≈15)로 회귀 확인.

## COMPLETENESS 자기점검 — 불확실/미결 항목

실제 코드 검증(위 4개 파일 정독) 후에도 남는 불확실성과 이 설계가 아직 못 덮은 것:

1. **프론트엔드 통합 미검증**: 나는 `components/chat/ChatPage.tsx`를 읽지 않았다. 세 탐색이 `LENS_PERSONAS`(84-86), `chatMode`(129), `canLens`(134), send(312), 메뉴(755-806)를 인용하나 라인은 미확인. 청중 서브메뉴가 2단계 드롭다운(세그먼트 타입 × 특정 단과대)을 어떻게 렌더할지, `chatMode` 상태가 `framing:{id}` 문자열을 그대로 담을 수 있는지 실측 필요.

2. **`loadAudienceSubstrate`의 "인사말/비전 강제 pin" 구현 세부 미확정**: `WikiAgent.getContext`(`wiki-agent.ts:96`)가 특정 overview를 질의 무관 항상 반환하는 옵션을 노출하는지 확인 안 됨. `options.chunkCap`은 있으나 "특정 타입 강제 회수"는 없을 수 있어, `loadData`로 raw overview를 직접 읽어 별도 `AgentContext`로 조립해야 할 가능성(CLAUDE.md §4.1 `loadData` 75-94). recency.ts의 "컨텍스트 직접 주입" 패턴이 참고 선례.

3. **`buildNumberedContexts`가 substrate + persona를 합칠 때 [N] 번호 순서**: lens는 canonical을 앞에 둬 낮은 [N]을 받는다(`route.ts:255`). framing도 동일하나, substrate(단과대 사실)와 stance가 섞일 때 인용 번호 충돌·중복 source 처리(`buildNumberedContexts`의 unique source 로직, `citations.ts`)를 실측 안 함. 특히 leesj stance와 college fact가 같은 topic일 때 dedup 거동 불확실.

4. **`enforceContextBudget` 적용 여부 미결**: lens 브랜치는 `budgetedContexts`(예산 적용됨)를 쓰지만, framing은 `loadAudienceSubstrate`로 우회 회수 → 예산 미적용. substrate가 클 때(humanities 인사말 2205자 + 23 entity) 토큰 폭증 가능. `enforceContextBudget(effectiveQuery, substrate, budgetChars)`를 명시 적용할지, 아니면 substrate가 이미 chunkCap으로 제한되는지 결정 필요.

5. **`avoidFrames`/`bannedTerms` 하드 필터의 실효성 미검증**: 프롬프트 지시만으로 "존재론적" 같은 금기어가 정말 안 나오는지는 실측(golden QA) 전엔 불확실. 사후 정규식 필터(`route.ts:553`의 `[missed-web]` 패턴처럼)로 금기어 검출 → 재작성 루프가 필요할 수 있으나 이 설계엔 미포함. 즉 톤 캘리브레이션은 프롬프트 few-shot에 의존하며 **신뢰도 상한**이 있다(프레이밍 노트 감사 블록이 인간 체크).

6. **`resonantStances[].stanceRef` ↔ 실제 leesj stance id 매핑 방식 미확정**: `loadPersonaContext`는 query 기반 RRF로 stance를 회수(`lens.ts:106-148`)하므로, 프로필이 지정한 `stanceRef`가 실제 회수 결과에 포함되는 보장이 없다. 프로필의 resonant 목록과 런타임 회수 결과가 어긋날 때(프로필은 4+1을 core라 하나 query가 그걸 안 끌어옴) 어느 쪽이 우선인지 로직 필요. → 프레이밍이 stance를 query 회수가 아니라 프로필 지정으로 강제 로드하는 별도 경로가 나을 수 있음(미설계).

7. **비용 미추산**: substrate(단과대 overview) + canonical + stance + 프로필 지시가 모두 입력 토큰. 특히 rich 단과대(humanities)는 lens보다 입력이 클 수 있음. `[chat-usage]` 로깅(`route.ts:537`)은 상속되나, framing 평균 입력 토큰/비용을 추산 안 함. MEMORY의 "비싼 LLM 작업은 비용 먼저 보고" 규율상, Phase 1 배포 전 예상 토큰·비용 측정 권장.

8. **`streamDirectAnswer` AnswerClass 3/4 분기와의 상호작용**: `route.ts:194`의 직답 분기는 `routing.college`가 있으면 발동. framing이 단과대를 타겟할 때 이 분기가 오발동해 LLM을 우회할 위험(직답이 프레이밍 대신 연락처/공지를 반환). framing 브랜치는 이 분기 *이후*이므로 안전해 보이나, `routing.answerClass`가 3/4로 나오는 college 질의에서 framing 요청이 어떻게 흐르는지 실측 미확인.

9. **`data/audiences.json`의 import 방식**: lens는 `agentsConfig`를 `import ... from '@/data/agents.config.json'`(`lens.ts:13`)로 정적 import. audiences.json도 동일 정적 import면 빌드 타임 번들에 포함(HMR 없이 재배포 필요) vs `fs.readFileSync`(`lens.ts:70` 방식) 런타임 로드. 저작 반복이 잦은 MVP엔 후자가 유리하나 미결정.

10. **단일 후보 하드코딩 부채**: `getPersonaConfig`(`lens.ts:49`)는 `personaId`로 조회하나 framing은 `'leesj'` 하드코딩(`route.ts` Edit 4). CLAUDE.md와 MEMORY(project_named_person_web_guard)가 leesj를 lensPersona로 격리 — 다후보 시 `getPersonaConfig`/`LENS_PERSONAS`/framing persona 파라미터 3곳 확장 필요. 이 설계는 단일 후보 전제.

## 1. Q1 직답 — 포용성·입도

### 1-(a) "충분히 세밀한가?" → **아니오. 양방향으로 틀렸다.**

현 설계(`청중 = wiki_id = 단과대`, 27개 평면 프로필)는 **입도가 부족한 동시에 과분할**이다.

- **입도 부족(under-granular):** 메시지 품질을 실제로 가르는 축은 "어느 단과대냐"가 아니라 **"어느 역할이냐"**다. 같은 공대 안에 정교수·조교수·학부생·대학원생·계약직·강사 최소 6청중이 있고, 이들의 pain·franchise·톤이 서로 정반대다. 검증된 사실이 이를 증언한다 — 설계 자신의 톤 다이얼 D1(철학깊이)×D2(레지스터)를 **세팅하는 변수가 역할이다.** "공대 정교수(D1 中·성과지표)"와 "공대 학부생(D1 低·체감어)"은 **하나의 `eng` 프로필에 D1 두 값을 담을 수 없다.** 즉 college-only 프로필로는 자기 톤 다이얼조차 세팅 불가.
- **과분할·중복(over-granular shell):** `data/leesj.json`의 stance 9개는 단과대별이 아니라 **정책 도메인(AI시대·후속세대·재정·국제화·인권·캠퍼스…)**으로 조직돼 있다. 후보 설득 재료의 자연 축은 "관심사"이지 "단과대"다. 단과대가 예측하는 정보량 대부분은 "규모 앵커(이미 stat-yearbook에 있음) + 지배적 학문군 태그"로 흡수되므로, 27개를 손으로 채우면 **90% 동일한 껍데기**가 된다(memory의 "thin" 관측과 일치).

**판정: 현재는 "세밀한 껍데기"다.** 세그먼트 자체(27 wiki_id)는 존재하나, 세밀함의 실익인 역할·관심사 변량이 프로필 안에 안 잡힌다.

### 1-(b) "충분히 포용적인가?" → **아니오. 축이 하나 빠져 구조적으로 못 담는다.**

영향력은 formal 투표권 하나가 아니라 **3종류**이고, college-centric 설계는 (A)의 일부만 덮는다:

- **(A) 정식 표 무게** — 추천위 27석 + 정책평가단(미정량). ROI 중심.
- **(B) 동원·여론(legitimacy)** — 학생단체·노조·대학원생. 표는 적지만 공론·집단행동을 만든다. **배제 시 "엘리트적" 서사 리스크.**
- **(C) 게이트키퍼** — 이사회·외부이사·평의원회. 설득 대상이 아니라 최종 관문(3배수→임용). 신뢰·거버넌스 레지스터가 필요.

**오너가 든 8개 누락 청중(직원·비정년·대학원생·학부생·학생단체·연구원·동문·노조) 중 college-centric이 온전히 덮는 건 0개다.** 특히 **직원(추천위 2석)·동문(외부위원 2석)은 formal 좌석까지 가진 유권체인데** 어떤 단과대 wiki_id에도 매핑되지 않는다.

**포용성 판정의 선결 조건 — 정책평가단 franchise 외부 확인.** 실제 후보정책을 평가하는 "유권자단"인데 구성비(교원/직원/학생 %)·가중치가 데이터에 전무하다(최우선 갭). **이걸 외부 확인하기 전에는 "모든 청중 포용"을 주장할 수 없다** — 진짜 무게중심이 어디인지 모르는 채로 그리는 지도이기 때문.

### 해법 — 축을 곱하지 말고 상속하라

정답은 다차원 매트릭스(cartesian)가 아니라 **3층 상속 + 1 런타임 오버레이**다:

```
resolvedAudience(role, org)
  = base[role]              // 두껍게: pain·priority·franchise·톤(D1×D2)·landmine
  ⊕ modifier[cluster(org)]  // 중간: 학문군 프레이밍 델타(연구/기초/예술/전문직)
  ⊕ leaf[org]               // 얇게, 데이터만: 규모앵커(stat-yearbook) + landmine 0~2
  → interestWeight(role,cluster)   // 저장 안 함: 관심사 가중벡터
  → selectStances(leesj 9 stance)  // foreground 인용 런타임 선택
```

`⊕` = 필드 오버라이드 + landmine 합집합(**곱셈 아님**). 이 구조가:
1. 역할·관심사 변량을 **명시 축으로 승격**(flat college가 놓친 것),
2. 톤을 **역할에 정박**시켜 "공대 교수 vs 학부생" 분기를 표현,
3. 27 단과대 껍데기를 **데이터 전용 leaf**로 축소,
4. 어떤 단과대에도 안 붙는 **교차 유권체(직원·동문·평의원·이사회)**를 별도 트랙으로 편입.

## 2. Q2 직답 — 데이터 규모·다양성·깊이

### 오너 전제 교정 — 상한 제약은 토큰이 아니다

오너의 "두꺼우면 토큰 과잉" 전제는 **틀렸고, 그게 스펙 전체를 바꾼다.** 프레이밍 질의는 거의 항상 **단일 청중**("공대 교원에게 닿을 메시지")이라 **쿼리당 프로필 1개**(많아야 3개)만 주입된다. 전체 27개는 **저장·유지 비용이지 쿼리당 토큰 비용이 아니다.** 진짜 상한 3개:

| 진짜 천장 | 실제 수치 |
|---|---|
| **① 캠프 검수 처리량(진짜 병목)** | pain·landmine·priority는 정치 민감 주장 → 캠프 사실확인 필수(hallucination 절대 불가). 27×(pain3+landmine2+priority5)≈**270개 검수 주장.** 이게 롤아웃 속도를 정한다. |
| **② estimate 신뢰도 전파** | 흔들리는 앵커(농생대 전임27 의심·정책평가단 미정량·fine-arts 비활성) 위에 두꺼운 프로필 쌓으면 오차 증폭. 앵커 검증 전엔 thin 유지. |
| **③ staleness** | pain·priority는 선거·이슈마다 drift. 두꺼운 필드일수록 갱신 주기 짧게 태깅. |
| ~~토큰~~ | 쿼리당 1프로필이라 사실상 미제약. 동시 주입만 **3개 하드캡.** |

### 필드별 min / ideal / cap (핵심 답)

| 필드 | min(미만이면 generic·무용) | ideal(품질 최적) | cap(초과 시 낭비) | 토큰(ideal) | 1차 조사 필요? |
|---|:--:|:--:|:--:|:--:|:--:|
| **dials** (D1·D2·evidenceMode) | 2+1 **전부 필수** | 동일 | — | ~40 | ✗ (설계+few-shot) |
| **priorities** (원하는 것, 순위有) | **3** | **5** | 7 | ~130 | ✔ |
| **painPoints** (현재 불만·불안) | **2** | **3~4** | 5 | ~150 | ✔ (정치민감·캠프검수) |
| **resonantStances** (leesj 9 중 닿는 것 → **ID+1줄**) | **2** | **3** | 5 | ~120 | ✗ (기존 참조, 신규 0) |
| **landmines** (건드리면 역효과) | **1** | **2** | 3 | ~120 | ✔ (고리스크) |
| **lexicon** (선호/기피 분리) | **8** | **12~15** | 20 | ~120 | ✗ (LLM 초안+스팟체크) |
| **translations** (generic→튜닝 rewrite 쌍) | **3** | **5** | 8 | ~500 | ✗ (캠프 자작) |
| **stat_anchor** (규모·의석) | 1 | 1 | 1 | ~50 | ✗ (기존) |

**generic 붕괴선(껍데기 탈출 최소):** dials(전부) + priorities≥3 + painPoints≥2 + resonantStances≥2 + landmines≥1 + lexicon≥8 + translations≥3쌍. **이 floor 미만이면 프로필 없는 것보다 나쁘다** — 규모만 알고 우선순위를 모르면서 "프로필이 있으니 맞겠지"라는 **false confidence로 generic·오톤 메시지**를 낳기 때문.

핵심 근거:
- **resonantStances = 가장 저렴·고가치·저리스크(⭐).** 후보 고유성의 다리(leesj 기존 입장 → 청중 우선순위). 신규 데이터 0(9 stance 이미 존재, ID만 참조), 검증리스크 낮음 → **27개+tier 전부에 우선 채운다.** 단 본문 복제 금지(중복 시 쿼리당 +1.8k×N 낭비), ID+1줄만.
- **translations = 톤 다이얼의 심장.** D1×D2 스칼라만으로 모델은 재현 못 한다. few-shot 5쌍이라야 (고추상 1·구체 1·landmine 회피 1·중간 2)로 레지스터 스팬을 덮는다. **캠프 자작 가능** → 1차 조사 전에도 채운다.

### 몇 개면 포용적인가 (N-곡선)

| N | 성격 | 판정 |
|:--:|---|---|
| 2 | PoC·스키마 검증 | ❌ 포용 아님 |
| **6~8** (medicine·eng·science·humanities·social·education +약학·음악) | **추천위 14석 단과대 교원 무게중심 대부분** | ✅ **실용 최소** |
| 15 (전 단과대+fine-arts) | college 축 완결 | 축-포용 |
| 27 (단과대+대학원) | wiki-parity | 시스템 정합 |
| **27 + ~5 횡단 tier**(전임전체·신진·직원·학생·동문) | Q1 "모든 청중" 성립 | **포용 주장 상한** |

### 깊이 vs 넓이 → **깊이 승(depth-first)**

1. 쿼리당 단일 청중이라 "27개 다 있어야 하는" 상황이 없다. **지금 겨냥하는 1개가 깊은 것**이 답변 품질을 지배.
2. **얕은 프로필은 음(-)의 가치.** thin이 최악일 수 있다(false confidence).
3. 넓이는 Q1(포용 주장)에만 필요한데, 그건 **정직한 thin + "저신뢰" 플래그**로 충족 — 가짜 deep으로 채우면 안 됨(자의적 생성 금지, memory).

→ **가중치-비례 3계층:** 무게중심 6~8은 full-spec, 나머지 단과대·top 대학원은 medium(floor), 횡단 tier·fine-arts는 thin 공용. **깊이는 formal-weight(추천위 14석)에 몰되, 존재(presence)는 모두에게** 부여.
